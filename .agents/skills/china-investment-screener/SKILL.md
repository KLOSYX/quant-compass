# 中国投资标的筛选

把用户的投资目的转化为明确约束，构建有来源、有日期、有淘汰记录的候选池。目标是提供决策支持，不是制造确定性买入指令。

## 先读取什么

- 涉及开放式基金、债基、货币基金或ETF时，读取 `references/data-sources.md`。
- 需要计算、排名或解释指标时，读取 `references/methodology.md`。
- 需要生成正式报告或用户提供蚂蚁/证券账户清单时，读取 `references/report-contract.md`。

## 工作流程

### 1. 明确目标

从对话中提取已有信息，避免重复询问。至少记录：

- 投资目的和期限；
- 初始资金、后续投入和一次性/定投方式；
- 最大可接受回撤或可接受亏损描述；
- 流动性、最低持有期和用钱时间；
- 目标收益是硬目标、参考目标还是仅希望跑赢某个基准；
- 允许和排除的品类；
- 购买渠道：蚂蚁、证券账户或其他；
- 已有持仓及是否允许重复暴露。

缺少的信息会显著改变结果时才询问。若用户无法量化风险，使用情景语言帮助其选择，例如“短期出现 10% 浮亏是否会卖出”，不要自行给用户贴风险等级。

### 2. 定义可购买状态

严格区分：

- `public_open`：公开数据显示开放申购；
- `ant_verified`：用户提供的蚂蚁页面、链接、截图或导出清单确认可买；
- `broker_exchange`：交易所上市，通常可通过合格证券账户交易；
- `unknown`：没有足够证据。

公开开放申购不等于用户的蚂蚁账户实时可买。没有渠道证据时写“待在蚂蚁确认”，不能写“蚂蚁可买”。

### 3. 构建候选池

优先使用广覆盖接口形成候选池，再逐只抓取历史数据。保留原始字段、获取时间和来源。先做品类内去重：同一底层策略的 A/C 份额、ETF 与联接基金不能被当成相互独立的分散投资。

不要声称覆盖“全市场”，除非记录了候选池总数、成功获取数、失败数、过滤数和最终样本数。否则使用“本次可验证候选池”。

### 4. 做硬过滤

硬过滤先于评分。结合用户目标检查：

- 申购/交易状态和渠道证据；
- 成立时间和足够的历史区间；
- 最低持有期、封闭期、赎回限制；
- 规模、清盘风险、成交额和买卖价差（场内产品）；
- 数据新鲜度、缺失率和异常值；
- 用户明确的回撤、期限、品类和流动性限制。

每个淘汰项保留原因。不要用一个总分掩盖硬性不适配。

### 5. 同类比较

使用 `scripts/analyze_candidates.py` 计算可复现指标。开放式基金的长期回报与回撤优先使用累计净值；单位净值可能遗漏分红影响。

先在同类内比较，再做目标适配：

- 收益：区间收益、年化收益、滚动收益；
- 风险：年化波动、最大回撤、最差月份、回撤修复；
- 稳定性：正收益月份比例、滚动区间胜率；
- 风险调整：夏普、卡玛，但在数据不足时不显示伪精确结果；
- 成本与可执行性：费率、申赎限制、场内流动性、渠道确认。

不要把股票基金、债基和货币基金直接按收益排成一个榜。跨品类比较回答的是“哪种风险预算更适合目标”。

### 6. 验证结论

- 对推荐候选检查最新数据日期和接口失败；
- 关键事实尽量使用第二来源或产品官方材料复核；
- 区分事实、计算结果和判断；
- 若历史短、数据缺失或渠道未确认，降低置信度并明确说明；
- 不把历史收益外推成未来收益，不使用“保本”“稳拿”“必涨”。

### 7. 输出

遵循 `references/report-contract.md`。默认给出 3 至 8 个候选，而不是单一答案。每个候选说明：适合原因、主要风险、不适用情景、渠道状态、数据日期和下一步核验动作。

## 脚本入口

离线或已有候选数据：

```powershell
python scripts/analyze_candidates.py --profile profile.json --nav nav.csv --products products.csv --output report.json
```

在线抓取公募基金数据：

```powershell
python scripts/fetch_akshare_funds.py --fund-type 债券型 --output-dir data
```

抓取脚本失败时保留失败清单，不要静默缩小样本后继续宣称全市场覆盖。

## 当前边界

第一版不自动覆盖银行存款、银行理财、保险年金、私募基金和券商收益凭证。这些产品没有统一可靠的个人实时可售接口。用户提供产品清单后，可以按相同的期限、流动性、费用和风险证据框架比较，但不要把业绩比较基准当成承诺收益。
